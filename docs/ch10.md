# 第 10 课 · 命令缓冲

> 对应源码：`lessons/10_command_buffers.cpp`
> 目标：理解 Vulkan 的"录制-提交"模型，写下第一条渲染命令。

## 10.1 为什么不是"调用即执行"

OpenGL 是**即时模式**：你调 `glDrawArrays`，驱动立刻把它变成 GPU 命令。每个 OpenGL 调用都要穿越用户态→内核态的边界，还要驱动在运行时反复猜测你的意图。

Vulkan 改走**录制-提交**模型：

```
录制阶段（CPU）                 提交阶段                执行阶段（GPU）
┌─────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│ 命令缓冲.reset() │    │ vkQueueSubmit(    │    │  GPU 按队列顺序   │
│ vkCmdBegin(...)  │ →  │   命令缓冲,       │ →  │  真正执行命令     │
│ vkCmdDraw(...)   │    │   等待/通知信号量  │    │                  │
│ vkCmdEnd(...)    │    │ )                 │    │                  │
└─────────────────┘    └──────────────────┘    └──────────────────┘
   只是往内存写指令         一次批量交接            与 CPU 并行
```

所有 `vkCmd*` 函数的真相：**它们不执行任何东西，只是往命令缓冲里写字节**。真正执行发生在 `vkQueueSubmit`，而且是异步的——提交完 CPU 立刻返回，GPU 还在后面慢慢跑。

这个模型是 Vulkan 多线程渲染的地基：录制可以在任意线程并行做（每线程一个命令池），只有提交受队列约束。

## 10.2 命令池：命令内存的分配器

命令缓冲不能凭空 new，要从**命令池**（Command Pool）分配：

```cpp
VkCommandPoolCreateInfo poolInfo{};
poolInfo.sType = VK_STRUCTURE_TYPE_COMMAND_POOL_CREATE_INFO;
poolInfo.flags = VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT;
poolInfo.queueFamilyIndex = queueFamilyIndices.graphicsFamily.value();
```

两个字段的讲究：

- `queueFamilyIndex`：**池和队列族绑定**——从池里分配的命令缓冲只能提交到该族的队列。这是 Vulkan 里少有的"隐性归属"约束
- `RESET_COMMAND_BUFFER_BIT`：允许单独 reset 缓冲（而不是只能整个池 reset）。要每帧复用同一条缓冲，这个标志必须开

## 10.3 分配与录制

```cpp
// 分配（句柄级，一次可分配多条）
vkAllocateCommandBuffers(device, &allocInfo, &commandBuffer);

// 录制
vkBeginCommandBuffer(commandBuffer, &beginInfo);      // 开卷
    vkCmdBeginRenderPass(commandBuffer, &renderPassInfo, VK_SUBPASS_CONTENTS_INLINE);
        vkCmdSetViewport(commandBuffer, 0, 1, &viewport);   // 动态状态的"填表"
        vkCmdSetScissor (commandBuffer, 0, 1, &scissor);
        vkCmdBindPipeline(commandBuffer, VK_PIPELINE_BIND_POINT_GRAPHICS, graphicsPipeline);
        vkCmdDraw(commandBuffer, 3, 1, 0, 0);               // 画！（还没执行）
    vkCmdEndRenderPass(commandBuffer);
vkEndCommandBuffer(commandBuffer);                    // 封卷
```

`vkCmdDraw(缓冲, 顶点数3, 实例数1, 首顶点0, 首实例0)`——本课没有顶点缓冲，顶点坐标是写死在顶点着色器里的，所以"3 个顶点"就足以召唤出三角形。这条 draw 命令此刻安静地躺在缓冲里，等下一课被提交。

注意录制顺序的层级感：render pass 包着 draw，begin/end 包着一切——Vulkan 命令缓冲是**有作用域结构的**，不是平铺的指令列表。

## 10.4 每帧复用：reset 再录

命令缓冲录一次不代表终身有效——交换链图像下标每帧变、视口可能变。所以流程是每帧：

```
reset(释放旧命令) → 重新录制 → 提交
```

正因为要反复录制，`RESET_COMMAND_BUFFER_BIT` 标志和"录制放在每帧循环里"的配合是标准姿势。

## 踩坑记录

- **`vkCmd*` 不报错 ≠ 执行成功**：录制期的错误大多在提交或 `vkDeviceWaitIdle` 时才暴露。调试时别只看录制函数的返回值
- **命令池的族归属**：把池建在呈现族却往图形队列提交，校验层会拦；多队列族项目里建池前先想清楚"这批命令给谁执行"
- **录到一半的缓冲不能提交**：`vkBeginCommandBuffer` 后忘了 `vkEndCommandBuffer` 就 submit，是 undefined behavior

## 小结

> 录制-提交：vkCmd* 只写字节、vkQueueSubmit 才真执行；命令池是命令内存的分配器且与队列族绑定；每帧 reset 再录是标准姿势。指令写好了，但"什么时候递笔、怎么防止画室撞车"还没解决——下一课：渲染呈现与同步，以及你人生中第一个 Vulkan 三角形。
