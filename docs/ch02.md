# 第 2 课 · 校验层

> 对应源码：`lessons/02_validation_layers.cpp`
> 目标：给开发期装上 Vulkan 官方"体检医生"，并学会**动态加载扩展函数**这个核心技术。

## 2.1 校验层是什么

Vulkan 以"零运行时检查"换性能——驱动默认假设你做的每件事都合法。代价是：犯了错不会报错，只会**花屏、死锁或静默崩溃**。校验层（Validation Layer）就是官方提供的"开发期外挂"：它在驱动和你的调用之间插一层，检查每个参数、每个状态组合，把问题用人话打印出来。

我们启用的是官方全家桶：`VK_LAYER_KHRONOS_validation`。

```cpp
const std::vector<const char*> validationLayers = {
    "VK_LAYER_KHRONOS_validation"
};
```

只在 Debug 构建启用（`NDEBUG` 未定义时），Release 编译为纯 `false`，零开销：

```cpp
#ifdef NDEBUG
    const bool enableValidationLayers = false;
#else
    const bool enableValidationLayers = true;
#endif
```

## 2.2 层 ≠ 扩展：两套正交的系统

学习时最容易混的一对概念，一次说清：

| | 层（Layer） | 扩展（Extension） |
|---|---|---|
| 是什么 | 插在调用链上的**检查器/拦截器** | 新增 API **功能** |
| 谁在用 | 开发期的你（Release 关掉） | 所有人，运行时也开着 |
| 本课代表 | `VK_LAYER_KHRONOS_validation` | `VK_EXT_debug_utils` |

注意本课**两个都要**：光有层，报错没人接收；光有扩展，没有检查器产生报错。类比：层是"医生"，扩展是"电话线"——医生在场 + 电话接通，诊断报告才能送到你手上。

```cpp
if (enableValidationLayers) {
    extensions.push_back(VK_EXT_DEBUG_UTILS_EXTENSION_NAME);  // 铺电话线
    createInfo.enabledLayerCount = ...;                       // 请医生到场
}
```

## 2.3 动态加载：扩展函数为什么"不存在"

尝试直接调用 `vkCreateDebugUtilsMessengerEXT` 会**链接失败**——它不在 `vulkan-1.lib` 的导入表里。因为扩展函数属于"可选模块"，加载器不能替每个驱动保证它们存在。Vulkan 的解法：按名字**运行时查找**。

```cpp
VkResult CreateDebugUtilsMessengerEXT(VkInstance instance,
    const VkDebugUtilsMessengerCreateInfoEXT* pCreateInfo,
    const VkAllocationCallbacks* pAllocator,
    VkDebugUtilsMessengerEXT* pDebugMessenger) {
    auto func = (PFN_vkCreateDebugUtilsMessengerEXT)
        vkGetInstanceProcAddr(instance, "vkCreateDebugUtilsMessengerEXT");
    if (func != nullptr) {
        return func(instance, pCreateInfo, pAllocator, pDebugMessenger);
    }
    return VK_ERROR_EXTENSION_NOT_PRESENT;
}
```

这就是著名的**壳函数模式**：自己写一个同名包装，内部用 `vkGetInstanceProcAddr` 按字符串查函数指针，查到就转发，查不到就返回"扩展不存在"。这个模式在第 6 课（交换链函数）、第 8 课之后还会反复出现，是 Vulkan 扩展机制的通用解法。

可以把它和操作系统类比：这就是 Windows 的 `GetProcAddress` / Linux 的 `dlsym` 同款思路——插件式加载函数指针。

## 2.4 Debug 回调：把报告接到自己的终端

校验消息默认打到 stderr，格式不可控。注册一个回调就能按严重级别过滤、自己排版：

```cpp
createInfo.messageSeverity =
      VK_DEBUG_UTILS_MESSAGE_SEVERITY_VERBOSE_BIT_EXT   // 最啰嗦的流水账
    | VK_DEBUG_UTILS_MESSAGE_SEVERITY_WARNING_BIT_EXT   // 警告
    | VK_DEBUG_UTILS_MESSAGE_SEVERITY_ERROR_BIT_EXT;    // 错误（必须留）

createInfo.messageType =
      VK_DEBUG_UTILS_MESSAGE_TYPE_GENERAL_BIT_EXT
    | VK_DEBUG_UTILS_MESSAGE_TYPE_VALIDATION_BIT_EXT
    | VK_DEBUG_UTILS_MESSAGE_TYPE_PERFORMANCE_BIT_EXT;

createInfo.pfnUserCallback = debugCallback;   // 你自己的打印函数
```

经验：**`VERBOSE` 可以关，但调试期建议全开**——很多"我怎么渲染不出来"的问题，最后都是一条被过滤掉的 verbose 消息道破天机。

## 2.5 为什么创建 messenger 要"两次"

这是本课最绕的设计，值得单独说：

```cpp
// 第一次：经 pNext 传"图纸"，不真正创建
populateDebugMessengerCreateInfo(debugCreateInfo);
createInfo.pNext = &debugCreateInfo;   // vkCreateInstance 的"附加条款"

// 第二次：实例建好后，正式创建长期有效的 messenger
setupDebugMessenger();
```

原因在于**鸡生蛋问题**：messenger 由实例的扩展函数创建，但实例创建过程中的错误（比如扩展名拼错）也需要被报告。Vulkan 的解法：创建实例时把回调"图纸"塞在 `pNext` 链里，加载器内部**临时**代建一个 messenger 覆盖这段窗口期；实例就绪后再正式建一个长期的。

`pNext` 是 Vulkan 里"给结构体追加额外条款"的通用机制——很多新功能都是以 `pNext` 挂进老结构的方式提供的，后面深度缓冲、多采样还会见到它。

## 踩坑记录

- **只在实例级启用层不够**：第 4 课创建设备时还要再声明一次设备级层，两道关缺一不可
- **`VK_EXT_DEBUG_UTILS_EXTENSION_NAME` 是个宏**：值就是字符串 `"VK_EXT_debug_utils"`，两种写法等价
- **回调里抛异常要小心**：回调可能被驱动的任意线程调用，直接 `throw` 可能穿越 C 边界——本教程选择打印后返回 `VK_FALSE`（不中止调用）

## 小结

> 层是检查器、扩展是功能，debug utils 两者都需要；扩展函数用 `vkGetInstanceProcAddr` 动态加载（壳函数模式）；`pNext` 挂图纸解决实例创建期的报错覆盖。装好这套系统，之后的每一课，校验层都会在你犯错时立刻拍肩膀——这是 Vulkan 学习期最重要的安全带。
